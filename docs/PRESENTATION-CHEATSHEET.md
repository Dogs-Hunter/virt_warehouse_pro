# Экспериментальный отказоустойчивый склад — шпаргалка для презентации

## Представление за 30 секунд

Это экспериментальная альтернативная реализация виртуального склада с упором на скорость, идемпотентность и отказоустойчивость. Она не заменяет основной стенд и не изменяет его код. В отличие от основного решения с Kafka и ClickHouse, здесь используются Rust, HAProxy, кластер NATS JetStream из трёх узлов, локальные WAL и Redb. Цель эксперимента — проверить, какую производительность можно получить на более компактной архитектуре, сохранив строгий запрет на потерю и двойное применение подтверждённых операций.

## Архитектура

```text
Клиент
  → HTTPS / API key
  → HAProxy 3.2 LTS
  → два приложения Rust (Axum + Tokio)
  → один активный writer, второй hot standby/read replica
  → NATS JetStream: три узла, replication factor 3, quorum 2/3
  → локальный WAL + snapshot
  → Redb: дедупликация, история и индексы чтения
  → Prometheus + Grafana
```

Роли компонентов:

- **HAProxy** принимает внешний трафик и переключает его между двумя приложениями.
- **Rust, Axum и Tokio** реализуют API и параллельную обработку операций.
- **NATS JetStream** выполняет роль канонического реплицированного журнала. Это альтернатива Kafka в эксперименте, а не Kafka под другим названием.
- **WAL** позволяет быстро восстановить локальное состояние после аварийного завершения процесса.
- **Redb** хранит дисковую дедупликацию, историю операций и индексы чтения.
- **Prometheus и Grafana** дают метрики и эксплуатационный контроль.

## Как проходит запись

1. HAProxy принимает JSON-запрос по HTTPS и проверяет API key.
2. Приложение валидирует данные и вычисляет отпечаток операции.
3. Проверяется `operation_id`: новый, точный повтор или конфликтующий повтор.
4. Активный writer подтверждает своё право записи через lease и fencing epoch.
5. Пакет записывается в NATS JetStream и подтверждается кворумом 2 из 3.
6. Операция попадает в локальный WAL и применяется к одной из 16 частей состояния.
7. Read-модель, история и дисковая дедупликация обновляются в фоне.
8. Клиент получает успешный ответ только после прохождения обязательного надёжного пути.

Внешний JSON используется только на границе API. Внутри журнала, WAL, snapshot и истории применяется компактный бинарный формат.

## Как проходит чтение

Чтение обслуживается из локальной Redb/read-модели без обращения к кворуму на каждый запрос. Реализованы одиночное и пакетное чтение, поиск по `operation_id`, индексы по владельцу и SKU, cursor pagination. Историческое чтение работает fail-closed: если индекс ещё восстанавливается, система не выдаёт неполный результат.

## Подтверждённая производительность

Последний тест целевого профиля **20% записи / 80% чтения**:

- смешанный поток: **495 956 операций/с**;
- чистое чтение: примерно **1,84–1,86 млн операций/с**;
- чистая запись: примерно **174 тыс. операций/с**;
- смешанный p95: **523,6 мс на пакетный запрос**;
- тестовый объём: **1 000 000 операций**.

Это результат конкретной локальной машины и пакетного теста, а не универсальная производительность production-системы. Одиночные запросы и другая инфраструктура дадут другие значения.

## Что проверено отдельными аварийными тестами

- SIGKILL приложения и восстановление без двойного применения.
- Остановка лидера JetStream во время нагрузки и выбор нового лидера.
- Потеря локального диска приложения и восстановление из кворумного журнала.
- Переключение между двумя приложениями.
- Потеря кворума: запись отклоняется, локальная «призрачная» операция не появляется.
- Падение после quorum commit, но до локального применения.
- Конкурентные и конфликтующие повторы `operation_id`.
- Повреждение WAL, snapshot и дискового индекса с карантином и восстановлением.
- Заполнение диска и последующее восстановление.
- Сетевое разделение и защита от устаревшего writer.
- Writer fencing с монотонной эпохой против split-brain.
- DLQ для повреждённых и несовместимых событий.
- Retention в режиме fail-closed: при переполнении новая запись отклоняется, старая история не удаляется молча.
- Полная потеря volumes и восстановление из внешней резервной копии.
- Rolling replacement приложений и миграция старого формата snapshot.
- TLS 1.3, API key и аутентификация NATS.
- Согласованность read-моделей двух приложений и фоновый history backfill.

## Главная гарантия

Короткая формулировка для защиты:

> Лучше вернуть временную ошибку, чем подтвердить запись, которую можно потерять или применить дважды.

Система использует fail-closed поведение. При отсутствии кворума, валидного writer lease, свободного диска или возможности безопасно сохранить операцию возвращается ошибка, а не ложный успех.

`operation_id` даёт идемпотентность:

- тот же ID и то же содержимое → `duplicate`, баланс не меняется;
- тот же ID и другое содержимое → HTTP 409;
- повтор после сбоя или неясного ответа безопасен.

## Особенности экспериментального решения

- Компактнее основного стенда: меньше тяжёлых внешних компонентов.
- Горячее чтение выполняется локально и не нагружает распределённый журнал.
- 16 частей состояния и 64 сегмента дедупликации уменьшают конкуренцию потоков.
- Пакетная обработка амортизирует сетевые вызовы, quorum commit и дисковые операции.
- Вторичные структуры обновляются асинхронно, но каноническая операция сначала фиксируется в кворуме.
- Состояние можно полностью перестроить из канонического журнала.
- Старые JSON-данные поддерживаются только для миграции; новые внутренние записи бинарные.

## Чем отличается от основного стенда

| Область | Основной стенд | Эксперимент |
|---|---|---|
| Журнал событий | Kafka | NATS JetStream |
| Аналитическое/историческое хранилище | ClickHouse | локальная Redb на каждом приложении |
| Приложение | архитектура основного стенда | Rust, Axum, Tokio |
| Входной балансировщик | инфраструктура стенда | HAProxy |
| Масштабирование истории | рассчитано на отдельное хранилище | ограничено локальным диском и backfill |
| Назначение | основной демонстрационный стенд | исследовательский прототип и проверка альтернатив |

Правильная позиция: эксперимент уже хорошо проверен на сбои, но основной стенд зрелее как распределённая платформа и лучше подходит для независимого масштабирования больших исторических данных.

## Что ещё не доведено до production

- Нет Kubernetes/оркестратора, автоматического размещения по разным физическим машинам и failure domains.
- Docker Compose на одной машине не доказывает устойчивость к потере целого дата-центра.
- Нет multi-region replication и формально измеренных RPO/RTO для разных региональных аварий.
- Redb — локальная embedded-база; историю нельзя масштабировать независимо так же удобно, как ClickHouse.
- API key и тестовые сертификаты — демонстрационный механизм, а не интеграция с Vault/KMS, OIDC и регулярной ротацией секретов.
- Нет полноценного централизованного tracing и production-процедур дежурства.
- Нет длительных soak-тестов на недели, формальной capacity-модели и теста на реальном сетевом/дисковом оборудовании.
- Не проведён независимый security audit и fuzzing всех бинарных форматов.
- Последняя оптимизация сегментированной дедупликации собрана, но её прирост ещё не измерен из-за сбоя Docker Desktop.

## Ответы на вероятные вопросы

### Почему NATS JetStream, а не Kafka?

Для эксперимента нужен был компактный журнал с репликацией, кворумом и быстрым запуском. JetStream проще развернуть в небольшом стенде. Kafka лучше знакома командам, имеет более широкую экосистему и зрелые сценарии больших потоков; эксперимент не доказывает, что JetStream всегда лучше Kafka.

### Почему нельзя просто записывать сразу в Redb?

Redb находится на локальном диске одного приложения. Потеря этой машины уничтожила бы единственную подтверждённую копию. Поэтому сначала используется реплицированный журнал трёх NATS-узлов, а Redb является восстанавливаемой read-моделью и индексом.

### Что будет при падении активного приложения?

HAProxy переводит трафик на резервное приложение. Резерв получает writer lease с новой эпохой, догоняет журнал и продолжает работу. Старый writer после возвращения не может применять записи со старой эпохой.

### Что будет при падении одного NATS-узла?

Остаются две реплики из трёх, поэтому кворум сохраняется и запись продолжается после выбора лидера.

### Что будет при падении двух NATS-узлов?

Кворума нет. Новые записи получают 503. Это намеренное безопасное поведение: доступность записи приносится в жертву согласованности и сохранности данных.

### Возможен ли split-brain между двумя приложениями?

Для защиты используются quorum-backed lease и монотонная fencing epoch, записанная в канонический журнал. Запись со старой эпохой сохраняется как диагностическое событие/DLQ, но к состоянию не применяется.

### Есть ли exactly-once?

Корректнее говорить не «магический exactly-once», а **идемпотентное применение**. Клиент может повторить запрос; уникальный `operation_id` и отпечаток содержимого гарантируют, что одна бизнес-операция не изменит баланс повторно.

### Почему p95 выглядит большим при высокой скорости?

Измеряется задержка пакетного запроса, а не одной операции. Один запрос содержит много операций и конкурирует с другими пакетами. Большой пакет даёт высокий общий throughput, но увеличивает время ответа всего пакета.

### Почему чистая запись медленнее чтения?

Запись проходит проверку дедупликации, writer fencing, сетевой quorum commit, WAL и применение состояния. Чтение берётся из локального готового индекса и не требует сетевого консенсуса.

### Не теряется ли операция из-за фонового обновления Redb?

Каноническая операция уже находится в реплицированном JetStream и локальном WAL. Redb можно перестроить. Успех вторичного индексирования не является единственной копией данных.

### Что произойдёт при заполнении диска?

Запись возвращает 503. После освобождения/замены локального хранилища состояние восстанавливается из кворумного журнала, а повтор клиентского запроса распознаётся как duplicate.

### Что произойдёт при повреждении локальных файлов?

Повреждённый файл не используется молча: он помещается в карантин, после чего состояние восстанавливается из доверенного журнала. Для snapshot и WAL используются проверки целостности.

### Почему два приложения, а NATS-узлов три?

Для консенсуса нужен нечётный состав: три узла выдерживают отказ одного. Приложения не образуют отдельный consensus-кластер: одно пишет, второе служит горячей репликой и кандидатом на writer.

### Можно ли горизонтально добавить ещё приложения?

Для чтения — концептуально да. Для записи текущая модель сознательно использует одного writer, поэтому простое добавление приложений не увеличит write throughput. Для этого потребуется разделение владения ключами или несколько независимых writer-partitions.

### Где сейчас главное узкое место?

Не JSON и не сам quorum. По последнему профилированию основное время находилось в предварительной дедупликации, очереди публикации и локальном применении. Поэтому дедупликация разделена на 64 сегмента; новый результат ещё предстоит измерить.

### Почему это называется недоработанным стендом, если тестов много?

Функциональная устойчивость проверена подробно, но production-ready определяется не только тестами кода. Нужны реальные failure domains, управление секретами, длительная эксплуатация, capacity planning, аудит безопасности, регламенты обновления и восстановление силами независимой команды.

### Может ли эксперимент заменить основной стенд?

Сейчас — нет. Он показывает жизнеспособную альтернативу и полезные инженерные идеи. Решение о замене потребовало бы одинакового набора нагрузочных данных, длительных тестов, расчёта стоимости владения и проверки на реальной инфраструктуре.

## Что лучше показать вживую

1. Схему компонентов.
2. Один успешный запрос и безопасный повтор с `duplicate`.
3. Графики Prometheus/Grafana.
4. Один заранее выбранный аварийный тест, а не все тесты подряд.
5. Последний отчёт 20/80.
6. Таблицу честных ограничений.

Для живой демонстрации лучше использовать тест переключения приложения или падения одного NATS-лидера. Разрушительные тесты volumes, полного диска и backup/restore лучше показывать записанными результатами: они дольше выполняются и повышают риск проблем с Docker во время презентации.

## Финальная формулировка

> Основной стенд показывает зрелую событийную архитектуру на Kafka и ClickHouse. Экспериментальный стенд проверяет другую точку дизайна: компактный кворумный журнал NATS JetStream, два быстрых Rust-приложения и локально восстанавливаемые read-модели. Он уже выдерживает ключевые аварии и показывает около 496 тысяч операций в секунду на профиле 20/80, но остаётся лабораторным прототипом до проверки на независимых машинах, длительной эксплуатации и внедрения production-контура безопасности.
