# Архитектура эксперимента

## Цель

Разделять стоимость гарантий и измерять её поэтапно. Первый baseline обеспечивает
durability на одном диске; следующие этапы добавят snapshot, репликацию, failover и
асинхронный аналитический sink.

## Горячий путь v0.1

```text
HTTP batch
   -> validation
   -> deterministic shard queues
   -> group-commit WAL + fdatasync
   -> per-shard balance update
   -> HTTP acknowledgement
```

Один writer собирает конкурентные операции в group commit. Состояние изменяет только
владелец шарда, поэтому для балансов не нужны mutex. Ключ шардирования — `(owner_id, sku)`.

## Инварианты

1. Подтверждённая операция уже находится в синхронизированном WAL.
2. Один `operation_id` применяется не более одного раза.
3. Все изменения одного `(owner_id, sku)` проходят через один shard-worker.
4. Повреждение завершённой WAL-записи обнаруживается CRC32.
5. Ошибка постоянного хранилища возвращает HTTP 503.

## Известные ограничения v0.1

- `operation_id` считается глобально уникальным только внутри шарда. Клиент не должен
  повторно использовать один ID для другого складского ключа.
- Дедупликационный индекс хранится в памяти и восстанавливается полным replay.
- Нет snapshots, compaction, репликации, read API, graceful drain и ограничения размера WAL.
- JSON выбран для удобства первого измерения; бинарный wire/WAL формат будет сравниваться
  после получения baseline.

## Репликация v0.2

Трёхузловой NATS JetStream хранит канонический журнал на трёх file-backed репликах.
HTTP batch публикуется как одна запись, а успешный ответ возможен только после JetStream
publish acknowledgement и локального WAL commit. При потере одного NATS-узла quorum 2/3
остаётся доступен. Локальный WAL пока используется для быстрого восстановления materialized
state. Перед открытием HTTP-порта приложение воспроизводит replicated stream поверх локального
состояния; дедупликация делает повторное применение безопасным. Поэтому потеря локального
application volume восстанавливается из quorum-журнала. Durable checkpoint позволяет обычному
перезапуску читать только ещё не применённый хвост stream.

Чтение catch-up выполняется с 64 параллельными запросами, но `buffered` выдаёт batches строго
в stream sequence-порядке. Таким образом сетевая задержка перекрывается без перестановки
операций при применении.

## Writer fencing

Право записи принадлежит одному application-узлу и хранится как CAS-обновляемый lease в
трёхрепличном JetStream KV. Lease имеет TTL 5 секунд и обновляется каждые 750 мс. Запрос
допускается к quorum publish только при локальном запасе lease не менее 2,5 секунд; publish
ограничен двумя секундами, после quorum ACK lease проверяется повторно. Потерявший lease узел
возвращает HTTP 503 и не изменяет локальное состояние. `/ready` доступен только текущему writer,
поэтому HAProxy автоматически направляет записи владельцу lease.
